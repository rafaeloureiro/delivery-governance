Delivery
Governance

Um projeto demonstrativo de organização, validação, transformação e disponibilização de dados de uma operação de delivery, com controles de acesso, proteção de informações pessoais, testes automatizados e indicadores operacionais.

Estrutura principal implementada Plataforma: Databricks Armazenamento: Delta Catálogo: delivery_governance 10 testes automatizados aprovados
01 · Resumo executivo

O que este projeto demonstra

O projeto parte de uma base de pedidos simulados e percorre um fluxo organizado em três camadas. Primeiro, os dados originais são preservados. Depois, os registros são avaliados e separados conforme regras de qualidade. Por fim, os dados aprovados alimentam indicadores consolidados e visualizações para análise.

Resultado principal: os dados foram organizados nas camadas Bronze, Silver e Gold. Foram criadas tabelas de pedidos válidos e rejeitados, indicadores operacionais e tabelas de resumo da qualidade. O projeto também inclui uma visualização analítica com CPF e e-mail mascarados, um dashboard com duas abas e uma suíte independente de 10 testes automatizados, todos aprovados na execução registrada.
02 · Arquitetura

Fluxo de dados

A arquitetura utiliza uma organização em camadas. Cada etapa tem uma responsabilidade clara, facilitando a rastreabilidade e a manutenção do processo.

Camada 1

Bronze

Preserva os dados recebidos, inclusive os registros que contêm problemas.

bronze.pedidos_raw
Camada 2

Silver

Armazena separadamente os registros aprovados e os rejeitados pela validação.

silver.pedidos_validos
silver.pedidos_rejeitados
Camada 3

Gold

Disponibiliza indicadores operacionais e tabelas consolidadas para análise.

gold.indicadores_delivery
gold.qualidade_resumo
gold.qualidade_por_motivo
Por que separar em camadas? A separação ajuda a preservar a origem, explicitar as regras de tratamento e disponibilizar dados preparados para consumo analítico sem misturar responsabilidades.

Componentes utilizados

  • Databricks: ambiente de desenvolvimento e processamento de dados.
  • PySpark: interface Python utilizada para transformar os dados com o mecanismo Apache Spark.
  • Delta Lake: formato de armazenamento utilizado nas tabelas do projeto.
  • Unity Catalog: camada de organização e controle de acesso aos dados.
03 · Qualidade dos dados

Validação e tratamento

Foram gerados 100 pedidos sintéticos. Para demonstrar o processo de qualidade, cinco registros receberam problemas intencionais, um problema por registro. As regras identificam esses casos e separam os dados aprovados dos rejeitados.

Distribuição após validação

95% aprovados
95 aprovados5 rejeitados

Regras aplicadas

  • Valor do pedido deve ser maior que zero.
  • E-mail do cliente deve estar preenchido.
  • Status deve pertencer aos valores reconhecidos.
  • Restaurante deve estar preenchido.
  • Identificador do cliente deve estar preenchido.

04 · Camadas de dados

Objetos criados

Os objetos abaixo estão organizados no catálogo delivery_governance.

Bronze — dados de origem

delivery_governance.bronze.pedidos_raw

Contém os 100 registros originais simulados, incluindo os cinco registros com problemas inseridos intencionalmente.

Silver — dados tratados e rejeitados

delivery_governance.silver.pedidos_validos — 95 registros aprovados.

delivery_governance.silver.pedidos_rejeitados — 5 registros rejeitados, acompanhados dos indicadores e motivos de rejeição.

Gold — dados preparados para análise

delivery_governance.gold.indicadores_delivery — indicadores operacionais agregados por restaurante.

delivery_governance.gold.qualidade_resumo — resumo consolidado dos indicadores de qualidade.

delivery_governance.gold.qualidade_por_motivo — quantidade de registros rejeitados por motivo.

delivery_governance.gold.pedidos_analiticos — visualização baseada nos pedidos válidos, com CPF e e-mail apresentados de forma mascarada.

Observação: as tabelas foram criadas no formato Delta. A visualização analítica é uma camada de apresentação; sua existência, isoladamente, não impede o acesso às tabelas de origem. Esse controle depende também das permissões configuradas no catálogo.

Mascaramento de informações pessoais

A visualização gold.pedidos_analiticos apresenta CPF (Cadastro de Pessoas Físicas) e e-mail em formato mascarado. A intenção é reduzir a exposição de informações pessoais em consultas analíticas.

Ressalva importante: o mascaramento na visualização não substitui o controle de acesso às tabelas subjacentes. O grupo de analistas não deve receber permissões de leitura sobre as tabelas originais que permitam contornar a apresentação mascarada.

Além disso, o compartilhamento do dashboard utiliza permissões individuais de dados: cada visualizador precisa ter acesso aos conjuntos de dados subjacentes.

Resultado da execução: o relatório do notebook registrou 10 testes, 10 aprovados, 0 reprovados e resultado geral APROVADO. O relatório final é um resumo da execução, não um teste adicional.
Evidência de reexecução: o notebook de processamento foi executado novamente. As contagens esperadas permaneceram em 100 registros na Bronze, 95 válidos e 5 rejeitados na Silver, e 5 restaurantes na agregação de indicadores Gold. A reconciliação confirmou 95 pedidos contabilizados na Gold. As gravações utilizam o modo overwrite, que substitui os dados existentes em vez de acrescentar cópias a cada execução.
Escopo da evidência: a reexecução foi testada com os mesmos dados sintéticos e as gravações atuais. Isso demonstra comportamento repetível nesse cenário, mas não equivale a uma garantia contra falhas parciais, concorrência ou mudanças futuras no código. O teste de proteção verifica a estrutura da visualização, não as permissões efetivas de acesso às tabelas originais.
08 · Orquestração

Execução automatizada do pipeline

O processamento e a validação foram organizados em um Job do Databricks. O Job coordena as tarefas e respeita a dependência configurada entre elas, evitando que os testes comecem antes da atualização das tabelas.

Tarefa 1

gerar_dados

Executa o notebook 00_gerar_dados, gera os dados sintéticos e atualiza as tabelas Bronze, Silver e Gold.

Succeeded · 1min 05s
Tarefa 2

testar_pipeline

Executa o notebook 01_testes_pipeline depois da conclusão bem-sucedida da primeira tarefa.

Succeeded · 18s
Execução mais recente registrada: o Job completo terminou com status Succeeded em 1 minuto e 23 segundos. As duas tarefas também apresentaram status Succeeded.
  • Ordem de execução: gerar_dados → testar_pipeline.
  • Dependência: a tarefa de testes depende da tarefa de geração dos dados.
  • Computação: ambiente Serverless do Databricks.
  • Forma de disparo validada: execução manual pelo comando Run now.
Escopo: a execução automatizada entre tarefas foi validada. Ainda não foi configurado um agendamento recorrente; portanto, o Job não inicia sozinho em horários definidos.
09 · Limitações e transparência

O que foi validado — e o que não foi

  • Os dados são sintéticos e foram criados para fins de demonstração; não representam uma operação real.
  • Os totais confirmados são 100 registros na origem, 95 aprovados, 5 rejeitados e 5 restaurantes na agregação de indicadores.
  • A matriz de permissões do grupo de analistas foi revisada na interface administrativa do catálogo.
  • O grupo possui leitura nas três tabelas Gold utilizadas para análise e não possui permissão de leitura concedida nas camadas Bronze e Silver.
  • O dashboard foi compartilhado com o grupo, mas o acesso não foi testado por uma segunda identidade independente.
  • O mascaramento foi verificado estruturalmente na visualização analítica, mas não representa, sozinho, uma comprovação de proteção efetiva contra todos os caminhos de acesso aos dados originais.
  • A execução do Job foi validada manualmente. Não há agendamento recorrente configurado.

Essas ressalvas fazem parte da documentação para diferenciar configuração, evidência observada e validação ainda necessária.

11 · Glossário

Termos utilizados

As siglas e expressões técnicas abaixo são explicadas para que a documentação também seja compreensível para pessoas de negócio.

DatabricksPlataforma para engenharia, processamento e análise de dados.
Apache SparkMecanismo distribuído para processar grandes volumes de dados.
PySparkInterface Python para trabalhar com o Apache Spark.
Delta LakeCamada de armazenamento que adiciona recursos de confiabilidade e controle às tabelas de dados.
Unity CatalogRecurso do Databricks para organizar, descobrir e controlar o acesso aos dados.
Bronze, Silver e GoldCamadas que representam, respectivamente, dados de origem, dados tratados e dados preparados para análise.
RBAC — Role-Based Access ControlControle de acesso baseado em funções ou grupos de usuários.
ETL — Extract, Transform, LoadExtração, transformação e carregamento de dados.
SQL — Structured Query LanguageLinguagem utilizada para consultar e manipular bancos de dados.
CPF — Cadastro de Pessoas FísicasIdentificador de pessoa física utilizado no Brasil.
MascaramentoExibição de uma versão parcialmente ocultada de uma informação, reduzindo sua exposição.
CatálogoContêiner de nível superior que organiza esquemas e objetos de dados.
EsquemaContêiner que organiza tabelas, visualizações e outros objetos dentro de um catálogo.
Visualização (view)Consulta salva que apresenta dados de uma ou mais tabelas sem necessariamente duplicar os dados.
Governança de dadosConjunto de práticas para assegurar organização, qualidade, segurança, responsabilidade e uso adequado dos dados.
IndicadorMétrica utilizada para acompanhar o desempenho de uma operação ou processo.
JobExecução configurada no Databricks para coordenar tarefas de processamento em uma sequência definida.
ServerlessModelo de computação em que a infraestrutura é gerenciada pela plataforma, sem necessidade de administrar diretamente os servidores.
DashboardPainel visual que reúne indicadores e gráficos para facilitar o acompanhamento de uma operação.
OverwriteModo de gravação que substitui os dados existentes no destino em vez de acrescentar novos registros.
