01 · Executive summary

What this project demonstrates

The project starts with a simulated order dataset and follows a structured, three-layer workflow. Original records are preserved first. Records are then evaluated and separated according to data quality rules. Finally, approved data feeds consolidated metrics and visualizations for analysis.

Key outcome: data was organized into Bronze, Silver and Gold layers. Valid and rejected order tables, operational metrics and data quality summary tables were created. The project also includes an analytical view with masked CPF and email fields, a two-tab dashboard, and a separate suite of 10 automated tests, all passing in the recorded run.
02 · Architecture

Data flow

The architecture uses a layered data organization. Each stage has a clear responsibility, making the process easier to trace and maintain.

Layer 1

Bronze

Preserves incoming data, including records that contain issues.

bronze.pedidos_raw
Layer 2

Silver

Stores records that pass validation separately from rejected records.

silver.pedidos_validos
silver.pedidos_rejeitados
Layer 3

Gold

Provides operational metrics and consolidated tables for analysis.

gold.indicadores_delivery
gold.qualidade_resumo
gold.qualidade_por_motivo
Why use separate layers? This separation preserves the source data, makes processing rules explicit, and provides analytics-ready data without mixing responsibilities.

Technology components

  • Databricks: development and data processing environment.
  • PySpark: Python interface used to transform data with the Apache Spark engine.
  • Delta Lake: storage format used by the project tables.
  • Unity Catalog: data organization and access control layer.
03 · Data quality

Validation and handling

One hundred synthetic orders were generated. To demonstrate data quality controls, five records were deliberately given issues, one issue per record. Validation rules identify these cases and separate accepted records from rejected ones.

Post-validation distribution

95% accepted
95 accepted5 rejected

Validation rules

  • Order value must be greater than zero.
  • Customer email must be provided.
  • Status must belong to the recognized values.
  • Restaurant information must be provided.
  • Customer identifier must be provided.

Administrative review outcome: read permissions on source tables were removed from the group. Read access was retained on the three Gold analytical tables required by the dashboard. The configuration was reviewed in the catalog permissions interface.

Masking personal information

The gold.pedidos_analiticos view displays CPF (Brazilian individual taxpayer identifier) and email in masked form. The goal is to reduce exposure of personal information in analytical queries.

Important caveat: masking in a view does not replace access controls on underlying tables. Analysts should not receive read permissions on original tables that would allow them to bypass the masked presentation.

Automated pipeline execution

Processing and validation were organized in a Databricks Job. The Job coordinates tasks and respects their configured dependency, preventing tests from starting before the tables have been updated.

Most recent recorded run: the complete Job finished with Succeeded status in 1 minute and 23 seconds. Both tasks also reported Succeeded.
  • Execution order: gerar_dados → testar_pipeline.
  • Dependency: the testing task depends on successful completion of the data generation task.
  • Compute: Databricks Serverless environment.
  • Validated trigger: manual execution using Run now.
Scope: task orchestration was validated. A recurring schedule has not been configured, so the Job does not start automatically at predefined times.
09 · Limitations and transparency

What was validated — and what was not

  • All data is synthetic and was created for demonstration purposes; it does not represent a real operation.
  • Confirmed totals are 100 source records, 95 accepted records, 5 rejected records and 5 restaurants in the metrics aggregation.
  • The analyst group's permission matrix was reviewed in the catalog administration interface.
  • The group has read access to the three Gold tables used for analysis and has not been granted read access to the Bronze and Silver layers.
  • The dashboard was shared with the group, but access was not tested using a second independent identity.
  • Masking was structurally verified in the analytical view, but this alone does not prove effective protection against every possible access path to the original data.
  • Job execution was validated manually. No recurring schedule is configured.

These caveats are documented to distinguish configuration, observed evidence and validation that is still required.

11 · Glossary

Key terms

The technical terms below are explained to make the documentation accessible to both technical and business audiences.

DatabricksA platform for data engineering, processing and analytics.
Apache SparkA distributed processing engine for large-scale data workloads.
PySparkThe Python interface for working with Apache Spark.
Delta LakeA storage layer that adds reliability and management features to data tables.
Unity CatalogDatabricks functionality for organizing, discovering and controlling access to data.
Bronze, Silver and GoldLayers representing source data, refined data and analytics-ready data, respectively.
RBAC — Role-Based Access ControlAn access control model based on user roles or groups.
ETL — Extract, Transform, LoadA process for extracting, transforming and loading data.
SQL — Structured Query LanguageA language used to query and manipulate databases.
CPFBrazilian individual taxpayer identifier.
Data maskingDisplaying a partially hidden version of information to reduce its exposure.
CatalogA top-level container that organizes schemas and data objects.
SchemaA container that organizes tables, views and other objects within a catalog.
ViewA saved query that presents data from one or more tables without necessarily duplicating the data.
Data governancePractices that support data organization, quality, security, accountability and appropriate use.
MetricA measure used to monitor the performance of an operation or process.
JobA Databricks execution configuration that coordinates processing tasks in a defined sequence.
ServerlessA compute model in which infrastructure is managed by the platform rather than directly by the user.
DashboardA visual panel that brings together metrics and charts to monitor an operation.
OverwriteA write mode that replaces existing destination data instead of appending new records.
